# Known limitations and documentation risks

Purpose: record material uncertainty so agents do not mistake a design intention or a mocked test for a production guarantee.

Read when: a task depends on deployment, a live portal, optional tooling, or a claim inherited from older documentation.

Source of truth: current source, configuration, tests, and workflow files. Entries are static observations and should be revisited when the referenced code changes.

## Current observations

| Area | Observation | Consequence |
| --- | --- | --- |
| EURES | `EURESFetcher` imports Playwright lazily, but Playwright is not listed in `requirements.txt` or `pyproject.toml`. | A live EURES scan requires an additional environment setup step that packaging metadata does not declare. |
| EURES dates | `EURESParser.parse_raw` accepts `target_date` but does not use it to filter vacancies. | Lambda passes the execution date, but EURES results can include records that would be excluded by the date-aware EPSO and eu-LISA parsers. |
| Gemini retries | [`GeminiValidator._validate_chunk`](../src/job_finder/gemini_validator.py) makes up to three total attempts (at most two retries). Each 429 failure sleeps 60 seconds and each 503 failure sleeps 10 seconds, including after the final attempt. Other errors sleep 2 seconds only when another attempt remains. | These are fixed delays, not exponential backoff. Three 429 failures add 180 seconds of sleep per chunk, excluding request and scan time; include this path when sizing Lambda timeouts. |
| Local `--no-ai` | The flag skips Gemini validation only. `main()` still calls `send_notifications` when findings exist. | Disabling AI does not make a run side-effect free. |
| Lambda output | `lambda_handler` sends configured notifications and returns a status object; it does not persist the findings report through the CLI exporters. | Operational documentation must distinguish Lambda notifications from local report files. |
| External services | Most tests use local fixtures and mocked HTTP or SDK calls. | A passing test suite does not validate current portal, API, credential, browser, or AWS availability. |
| SODETEGC status scope | The monitor compares only the currently visible, owned `Convocatorias abiertas` section on the official employment page with the fixed reference “Actualmente no hay ninguna convocatoria abierta”. A bounded page capture on 2026-09-24 returned HTTP 200 and showed that reference; future markup and availability are not established. | A notice means the recognized section differs from that reference and needs manual review. It does not establish a vacancy, IT relevance, or eligibility. Reworded reference text, changed page identity, missing structure, or fetch errors can be unverifiable rather than alertable. `target_date` cannot reconstruct past page state. |
| SODETEGC repeated notices and runtime | The status comparison stores no prior state. Deterministic tests cover independent baseline/changed/changed/baseline scans, and HTTP test calls are mocked. | Every successful scan while the section differs produces another notice. The bounded captured response and local tests do not verify future portal markup, notification delivery, live AI behaviour, or Lambda runtime suitability. |
| Guaguas document scope | The integration preserves the bases URL but does not download bases PDFs or include the `Avisos` history in normalized text. | An IT role mentioned only inside a bases PDF can be missed, and a deadline extension published only in an aviso is not interpreted automatically. |
| Guaguas historical dates | A historical target date is applied to the Guaguas HTML currently available at scan time. | The scanner cannot reconstruct what the portal displayed on that historical date. |
| GEURSA section inclusion | GEURSA includes every process under the current page's `Convocatorias en vigor` section, regardless of its application deadline. | Section membership is not evidence that applications remain open; past, future, and missing deadline wording is retained as information. |
| GEURSA historical dates | GEURSA accepts `target_date` for shared interface compatibility but does not use it to filter records or retrieve historical page state. | Supplying a historical date does not reproduce the website as it appeared then. |
| GEURSA HTML scope | GEURSA extraction is HTML-only and does not inspect requirements or IT roles found only in Bases or other linked PDFs. | A relevant role present only in an attachment can be missed. Attachment captions are kept out of normalized filter text. |
| GEURSA live fetch | A separate read-only check fetched one live response through `GeursaFetcher` on 2026-09-09, parsed one active card, and found zero IT matches; it did not invoke AI, notifications, or attachment downloads. | This is a single runtime observation, not a guarantee of future reachability, complete portal coverage, or unchanged markup. |
| GSC HTML scope | `GSCParser` reads only direct articles under the owned `.projects_holder.portfolio_main_holder` inside `#seleccion` and uses only the owned title heading/anchor. It does not inspect detail pages, PDFs, attachment captions, category text, or unrelated holders. | IT requirements, status changes, or application information visible only outside the title can be missed. |
| GSC date heuristic | GSC inclusion uses the leading publication date through publication plus seven calendar days, with inclusive boundaries. The inferred end date is a user-defined monitoring heuristic, not an official application deadline. | A listing can be monitored after an official deadline or excluded before an official process ends; detail/PDF deadlines were not inspected. |
| GSC historical dates | A historical target date is applied to the current GSC HTML response. | The scanner cannot reconstruct what the portal displayed on that historical date. |
| GSC pagination | The implementation scans all direct cards in the bounded holder but adds no pagination or load-more retrieval. The inspected snapshot had no pagination controls; a generic `infinitescroll.min.js` include was not treated as proof of more records. | Future markup that hides records behind pagination or client-side loading may be missed until separately supported. |
| GSC repeated scans | No persistent cross-run deduplication has been introduced for GSC. | Repeated scans within the inferred window can repeat findings or notifications. |
| GSC live verification | The implementation run used synthetic fixtures and did not establish a new live GSC runtime check. | Fixture tests do not prove current reachability, browser parity, official application status, future availability, or completeness of the external archive. |
| FULP discovery scope | `FulpParser` parses the current public `.panel_ofertas` response, reconciles its advertised total when possible, deduplicates numeric IDs, and reports unsupported pagination or continuation evidence without following it. | A current response is not a permanent catalogue-completeness guarantee; records hidden behind future pagination, client-side loading, or changed markup can be missed. |
| FULP request budget | Each logical online scan schedules at most 200 HTTP attempts within a 180-second scheduling budget, including listing, details, and manual redirect hops. Requests use bounded connect/read timeouts and no retry policy. | A large or slow listing can stop detail processing early. The scheduling deadline prevents new requests but cannot cancel a request already in flight, so wall-clock runtime can exceed 180 seconds. |
| FULP detail failures | Detail requests and parses are isolated per deduplicated numeric ID; failures are skipped and recorded in diagnostics, and a budget stop records remaining IDs separately from discovery completeness. | The returned findings can be a partial detail catalogue even when the listing response itself was successfully parsed. Diagnostics must be retained when assessing coverage. |
| FULP offline and availability scope | Offline details require valid canonical or `og:url` identity and conflicting or nested foreign identities are quarantined. Offline listings produce explicitly limited listing evidence and do not fetch details. `target_date` evaluates only explicit application-deadline wording in current HTML; publication dates are metadata and historical portal state is unavailable. Closure words in qualifications/duties are not status evidence, and interval deadlines use their closing date. | Offline and historical scans cannot establish full eligibility, current status, or what FULP displayed on the requested past date. Unknown or ambiguous availability is retained as uncertainty rather than assumed open. |
| FULP metadata and AI window | Findings retain an evidenced employer or `Empresa no identificada`, keep `source=FULP`, and recognise only standalone locality values rather than substrings in company names. Deterministic bounded sentence-unit prefixes of requirements, description, tasks, and profile are placed early; a unit that would exceed its section budget is preserved intact in that section's continuation, with no summarization or duplication. | Employer/location values not explicitly published by the page remain unknown; evidence beyond the existing 1,500-character validator window remains unavailable to AI, and early ordering cannot guarantee every long section's later wording reaches the model. |
| FULP live and scheduled verification | A bounded 2026-09-16 read-only check used one public listing response and six distinct detail URLs; it did not invoke AI, send notifications, deploy, or exercise Lambda. No persistent cross-run deduplication was added. | Current reachability, complete detail coverage, live Gemini classification, Lambda timeout/memory suitability, and notification behaviour remain unverified; repeated scheduled scans can repeat findings. |
| Indra catalogue coverage | The default Indra path uses the blank `/search/` catalogue and follows server-rendered pagination until links, repeated results/bodies, totals, or a safety bound indicate otherwise. It tracks scheduled page identities, so duplicate links and ordinary cycles do not by themselves imply missing coverage. The 2026-09-15 planning snapshot reported 739 unique IDs across 30 pages, with 14 jobs on the final page. A later read-only check sent one blank request plus 30 pagination requests, parsed 31 pages, observed 763 genuine rows and 733 unique IDs, and saw advertised totals of 738 and 739. A separate bounded discovery-only check after the repair parsed 30 pages, discovered 732 unique IDs, and reported complete coverage at that moment. | The earlier live check was incomplete after contradictory totals and a repeated-page diagnostic; the repeated `startrow=475` was a client diagnostic, not an established portal cause. The later complete result is only a point-in-time discovery observation and did not run the full detail pass. A full run can issue one request per discovered page plus one detail request per deduplicated listing, and changing portal markup, caps, redirects, or failures can make coverage incomplete. |
| Indra configured discovery | `portal_search_keywords` is optional; a non-empty list deliberately narrows discovery and is not reconciled with the blank catalogue or category directories. | Configured terms can miss jobs that the full catalogue would expose. Query terms are discovery inputs only and cannot create shared-filter matches. |
| Indra no-match and pagination | `#noresults` takes precedence over suggestion rows, and pagination follows official `/search/` links resolved against the current page. Query/locale preservation, omitted-sort inheritance, conflicting-order rejection, narrower-filter rejection, scheduled identity deduplication, repeated-result detection, total checks, and safety-bound diagnostics are source-tested. | These safeguards report known incompleteness but cannot prove that an external portal exposed every record or that its result count was internally consistent. |
| Indra geography and offline HTML | Geographic eligibility uses structured work-mode/location evidence. Portugal/PT/PRT and Brazil/Brasil/BR/BRA evidence is rejected before remote, Indiferente, or Gran Canaria acceptance, including when an excluded component appears in conflicting or multi-country values. Non-excluded country conflicts do not add a new rejection and continue through the existing mode/location policy. Country recognition is limited to exact delimiter-separated components, with a trailing parenthetical annotation ignored; street/client prose is not geocoded. Missing or unrecognised mode is not treated as remote; an offline listing snapshot cannot supply absent detail modality and is not fetched. Description prose is not used as country evidence. | Relevant jobs with insufficient or unusually formatted location evidence can be rejected or remain unknown. The policy does not infer geography from language, nationality, employer or client references, does not resolve cities to countries, and does not establish international contractual eligibility or residence restrictions. |
| Indra AI input | Indra candidates use the unchanged shared first filter and optional Gemini path. The application-supplied source field activates the [configured Indra-only AI preference](configuration.md#gemini-prompt-and-indra-only-preference) for core SAP, named-platform and dedicated SAST/DAST specialisation; incidental tool use, Power BI-focused work and SAP data integration remain eligible under that prompt. Gemini receives at most the first 1,500 characters of the normalized paragraph. | Requirements or contractual wording beyond that window can be unavailable to AI. With `--no-ai`, the Indra role preference is not applied, while parser-stage country exclusion still applies. Mocked validator tests establish plumbing only, not live semantic classification or API availability; SDK, network, or schema failures retain candidates under the existing fail-open fallback. |
| Indra repeated scans | Indra deduplicates IDs within one scan before detail and AI processing, but no persistent cross-run identity store was added. | Repeated scheduled scans can repeat findings or notifications. |
| Indra Lambda suitability | The source is included in the `ALL`/default and `ES` source groups, but no deployment or scheduled runtime check was performed for this integration. | Request volume, portal latency, Lambda timeout, memory, and external reachability remain unverified for production scheduling. |
| Deployment and manual scans | `deploy.yml` builds, uploads, updates and checks status without invoking. `run-scan.yml` requires explicit manual publishing and disables CLI invocation retries. | Pushes still update production code. Disconnected clients can leave Lambda running; manual reruns and scheduled invocations can still repeat notifications because no persistent deduplication exists. |
| Dependency policy | `AGENTS.md` requires exact requirement pins, while `requirements.txt` currently uses `python-dotenv>=1.2.2`. | This is a policy/configuration mismatch; documentation should expose it rather than imply compliance. |
| Index evidence | The codebase-memory index is useful for discovery but may report stale metadata or partial parsing. | Agents must verify material conclusions against source and coverage status. |

## How to report a new limitation

Record the affected path, the observed behaviour, the evidence type, and the practical consequence. Do not speculate about an external system without a check. Remove or revise an entry when the implementation and relevant verification demonstrate that it no longer applies.
